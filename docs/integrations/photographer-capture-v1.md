# Photographer capture REST v1

This [OpenAPI candidate](photographer-capture-v1.openapi.yaml) covers a paired, externally triggered still-capture sequence for [Fresnel #139](https://github.com/carstenartur/Fresnel/issues/139). The [fixtures](photographer-capture-v1.fixtures.json) use synthetic profiles, rasters and source images. The rules below are part of the contract.

## Pairing, discovery and revocation

Use the administrator-configured Photographer origin. Require HTTPS off loopback unless administrators explicitly trust the container network. Reject redirects to another origin. Fresnel exchanges a short-lived, single-use, rate-limited code over this connection and stores the opaque bearer token server-side. Photographer stores a strong token hash. Keep codes, tokens and private camera details out of diagnostics and logs. Use `Cache-Control: private, no-store` on pairing and service responses.

The pairing request offers one protocol major in `fresnelProtocolVersion`. Fresnel offers `1` to use this contract. A server that cannot serve the offered major returns `409 INCOMPATIBLE` without consuming the pairing code. The successful descriptor's supported range must include 1. Its authenticated health response is a current server observation. Fresnel derives its own connection state from recent authenticated exchanges and transport failures. An accepted code returns a token once, even when the same pairing request and key are replayed. If the response is lost, revoke the orphaned pairing in Photographer and issue a fresh code.

Authorize the bearer, its scope and resource ownership before idempotency lookup, camera dispatch or conditional media reads. A missing, invalid or revoked token receives `401 AUTHENTICATION_FAILED` with a bearer challenge. A missing scope receives `403 INSUFFICIENT_SCOPE`. A resource outside the pairing receives the same 404 as a missing resource of that type. Photographer's admin revoke action immediately invalidates the token and fences new shutter dispatches. Already dispatched work may reach a safe stopping point and commit its media locally. Restore settings and release the lease on the safe stop path. Fresnel can distinguish confirmed revocation from an otherwise generic authentication failure when it has local evidence of the revocation.

`fresnel:capture-sessions:write` permits the completion asset metadata embedded in capture status, trigger results and events. This lets Fresnel track which step completed. Each dedicated `/assets` resource route, including `GET .../metadata`, `HEAD` and source `GET` with or without `Range`, requires `fresnel:media:read` and pairing ownership. A capture-only token receives 403 at those routes.

## Map the device and validate the plan

| Fresnel measurement core | REST v1 |
| --- | --- |
| `CaptureProvider.Device.id` from discovery | `Camera.cameraProfileId`, copied verbatim |
| `CapturePlan.deviceId` in a create request | `CapturePlan.cameraProfileId`, copied verbatim |
| `CapturePlan.Requirements.preferredImageFormat` | `requestedSettings.preferredFormat` |
| `CapturePlan.Step.settleDelay` | `settleDelayMs`, whole milliseconds |
| `CapturePlan.Step` and `CaptureProvider.StepTrigger` pattern fields | `externalPatternId` and `externalPatternSha256` in both JSON bodies |
| Durable local experiment ID | `externalExperimentId`, used for correlation |
| Remote session ID | `sessionId`, persisted with the paired instance identity |

Keep device selections scoped to the paired `instanceId`. Keep camera, session and asset mappings in the server-side experiment. Before using a remote ID, Fresnel verifies that the caller owns or is authorized for that local experiment and uses its stored pairing. Browser-supplied remote IDs cannot act as authorization. Reject a profile missing from that instance or unavailable to the pairing. Return a stable opaque alias as `cameraProfileId` if the internal profile key is private or outside the wire ID grammar. Fresnel uses the advertised ID verbatim in both cases. Return redacted discovery fields only.

Accept UTF-8 JSON bodies up to 128 KiB after HTTP framing. Reject content codings, duplicate keys and unknown request fields. Require unique step IDs and zero-based sequence indexes equal to their array positions. Limit each settle delay to 30 seconds and cumulative declared settle time to the smaller of 30 minutes and the advertised session duration. Enforce advertised step, asset and session limits. This slice accepts `EXTERNAL` triggers and bounded JPEG or PNG source capture. Reject any required format or lock the profile cannot provide before creating the session or contacting the camera. Return the effective settings and preserve the plan's steps. Adapter implementations can reconstruct the core effective plan from both.

## Bind each trigger to the presented condition

For a displayed pattern, compute SHA-256 over this exact byte sequence.

1. ASCII `FRESNEL-PATTERN-RGB8-V1` followed by a single zero byte.
2. Positive width and height, each written as an unsigned 32-bit big-endian integer.
3. The presented source raster in sRGB with 8-bit red, green and blue samples, left to right and top to bottom, with three bytes per pixel. Composite any transparency before hashing. Omit row padding, encoding metadata and file headers.

Hash the raster actually staged for presentation after Fresnel applies software cropping, compositing or resampling. If these operations change the planned raster, rebuild the plan before triggering. The digest identifies the staged pixels independently of file encoding, display hardware and the camera's source image. A pattern ID maps to one hash within the plan. The trigger must carry the same ID and hash as its step. A physical-only BOS condition omits both fields and still includes `presentedAt` after the operator confirms it.

Fresnel's display workflow acknowledges the raster after rendering and settling, then triggers while the condition remains in place. Photographer compares the trigger to the immutable plan and uses its own monotonic clock to wait the declared settle interval after acceptance. `presentedAt` records Fresnel's observation. [Photometric-stereo browser acknowledgement](https://github.com/carstenartur/Fresnel/issues/141)

When Fresnel loses presentation or can no longer verify that the acknowledged condition remains in place, it stops sending and replaying triggers for that session. It requests cancellation with one persisted `Idempotency-Key`, retries that cancel with the same key if the response is lost, and polls for the outcome. If cancellation wins the dispatch race, the queued step never starts. An already dispatched shot may reach a safe stopping point and Photographer may commit its original result. Fresnel discards that exposure from the experiment unless it verifies continuity of the acknowledged condition through capture. Apply the same rule when Fresnel reconnects or restarts with an in-progress presentation it can no longer verify.

## Persist the trigger before touching the camera

- Scope create keys to the pairing and session collection. Scope trigger and cancel keys to the pairing, operation and session. Store the SHA-256 of the exact received UTF-8 JSON body for create and trigger, and of the empty body for cancel. Bind each trigger key to its original step ID. Fresnel persists the original body and key before sending. After authorization and basic request bounds checks, compare an existing key before step state, pattern or recovery checks. A changed step ID or changed request bytes receives `409 IDEMPOTENCY_CONFLICT`. Keep the key and result through restart, while the session is active or retained, and for at least the advertised `idempotencyRetentionSeconds` following terminal state. Fresnel stops unattended create retries once it is outside the guaranteed replay window.
- Atomically reserve the next eligible step and its key before work starts. Hold one logical camera lease for the active sequence and validate it before a state change. Record an irreversible dispatch fence before invoking the shutter. Serialize entry into the camera call with cancellation and revocation. Use a backend capture call with automatic retries of ambiguous shutter operations disabled.
- Treat an identical pending replay during active execution as `202` and an identical verified committed replay as `200` with the original asset. A new key on a previously reserved or completed step receives `409 STEP_ALREADY_TRIGGERED` outside recovery. Persist source bytes, metadata and their completion record before exposing the asset or moving to the next step. The capture worker never schedules work in response to a replay.
- Bound external-trigger waits by `maximumTriggerWaitMs`. On wait timeout, pause, restore settings and release the lease. Accept a cancel only after persisting the stop and fencing undispatched work. Identical cancellations return `204` through restart. Further triggers cannot start after the stop. A terminal session accepts cancel without changing its state.
- Capture status and event cursors survive restart. Return a bounded page with only committed event IDs. The client advances to the last returned ID.

The terminal session states are `COMPLETED`, `FAILED` and `CANCELLED`. `SessionStatus` includes `failure` exactly when its state is `FAILED`. A step is completed only when it has an immutable source result. `RECOVERY_REQUIRED` can represent multiple causes and never grants permission to fire again.

The provider SPI returns `StepResult` synchronously. On a REST `202`, the Fresnel adapter polls session status with a bounded deadline and backoff until the matching step exposes its result. Verify that the result and asset match the requested session ID, step ID and planned role before returning. If a result is unavailable, report the mapped provider failure on `FAILED`, a nonretryable conflict on recovery or other terminal state, or a retryable transport failure when the deadline expires. Preserve the original key and request bytes. If presentation continuity is lost while polling, request cancellation as described above.

## Recover after restart

Before accepting capture work, fence dispatches for every persisted nonterminal session and discard its queued work. This applies to sessions that were created, ready, waiting, paused, reserving a step or persisting media when the process stopped. Resume any durable cancellation through safe cleanup. Otherwise persist `RECOVERY_REQUIRED` for the session and record the transition once. Record `RECOVERY_REQUIRED` on a reserved step without a verified committed result, including when the reservation was persisted before a dispatch marker. Leave unreserved steps pending and fenced. A dispatch marker without committed media means the shutter may have fired.

Check the original length and SHA-256 of committed assets during recovery. Keep each verified step result and its original asset identity. Its identical replay returns `200` without contacting the camera, including after cancellation. An unfinished step in a recovery-fenced session returns `409 RECOVERY_REQUIRED` regardless of whether it has a reservation or the request uses a new key. A known key with changed request bytes still returns `409 IDEMPOTENCY_CONFLICT`. A result whose original bytes fail verification remains fenced and unavailable.

On recovery, revalidate lease ownership and any saved settings snapshot before restoring camera settings. Use the existing lease authority for safe restoration and release only the recovering session's lease. Leave a camera with uncertain or conflicting ownership untouched. Automatic cleanup never reacquires a lease for capture, and the persisted dispatch fence stays in place after cleanup. After an accepted cancel, persist `CANCELLED` once safe cleanup succeeds. Mark steps known to have never dispatched as `CANCELLED`, preserve verified completed results and retain `RECOVERY_REQUIRED` on any step with an uncertain shutter outcome. While safe cleanup remains unresolved, continue reporting `RECOVERY_REQUIRED` for the session even though the cancel was accepted. Further capture requires operator reconciliation.

## Verify the complete media representation

Pin the paired instance, session and asset IDs with the original media type, full length and SHA-256 from committed metadata. The strong ETag is the quoted lowercase checksum of the complete uncoded asset. A full GET returns `200`, length and media type. HEAD returns the same representation headers with no body and ignores range headers. After authorization, evaluate `If-None-Match` first. A wildcard or any matching entity-tag in its list returns `304` with the ETag. Use weak entity-tag comparison for that check. For GET with `Range`, evaluate `If-Range` before processing the range. Only an exact strong match selects partial content when `If-Range` is present.

For resume, request one inclusive `bytes=start-end` range with `If-Range` set to the original strong ETag and request identity encoding. Append a `206` only if the ETag, content type, start offset, response length and total from `Content-Range` match expectations. The server clamps the end to the last available byte. An unsatisfiable start returns `416 RANGE_NOT_SATISFIABLE` with `Content-Range: bytes */length`. If range processing is reached, reject malformed or unsupported ranges with `400 INVALID_REQUEST`. A stale validator yields a full `200`. Drop the local prefix and check that full response against the original pinned identity, length and hash. A changed ETag, different metadata or mismatched bytes fails integrity even if a subsequent metadata response describes the substitute consistently. Import only after verifying the assembled length and checksum. [HTTP semantics](https://www.rfc-editor.org/rfc/rfc9110.html#name-range-requests)

## Compatibility and next implementation slice

Use stable sanitized problem codes and [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html) problem objects. Return 400 for invalid request shape, 422 `INVALID_PLAN` for invalid plan relationships and 422 `PATTERN_MISMATCH` for a trigger that conflicts with a planned pattern or physical condition. Distinguish a lease conflict, an idempotency conflict and an uncertain shutter. Keep error text bounded. Clients ignore additive response fields and unknown optional capabilities. An unknown state prevents automatic progression until the client can interpret it. New required request semantics, changed state or authorization meaning, and changed media integrity rules require a new major version.

The next implementation slice pins the reviewed OpenAPI and fixtures by digest in both builds and runs them through a deterministic paired mock-camera session. Exercise the mock through Photographer's existing shared camera lease manager. Verify that one lease spans the sequence, a competing owner receives a typed conflict before any camera call, and cleanup releases the lease. An unmanaged mock can validate HTTP behavior only. Photographer admin UI and token storage, Fresnel pairing UI and adapter, SSE, online pause/resume and operator reconciliation, RAW previews, production deployment and the BOS and display photometric-stereo clients follow separately. This contract's fixtures exercise polling and Photographer-admin revocation. An endpoint for Fresnel-initiated remote revocation is a follow-up decision.
